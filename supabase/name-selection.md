# 観劇記録の名前選択

観劇記録・アーカイブは、登録済みの名前を選ぶ方式です。利用者のパスワード入力は不要です。クイズの `players` は別の一覧のままです。

## 名前の管理と既存記録

- 名前の一覧は Supabase **Table Editor → `profiles`** の `display_name` です。公開用クライアントで一覧と選択した名前を読み取り、管理用キーの設定には依存しません。
- 既存の `profiles.id` をそのまま選択します。`theater_logs.user_id`、同行者、個人タイムライン、比較・集計のIDは変えません。
- 名前は前後の空白を除いて保存します。重複判定はUnicode NFKC・前後の空白除去・英字の小文字化で揃えます。同じ表記や全半角・大小文字違いの名前をアプリから重複登録できません。
- 選択したIDだけをHTTP-only・SameSite=LaxのCookieに保存し、サーバーで実在するプロフィールか確認します。解除や別の名前への切り替えもできます。
- これは個人・知人向けの名前選択で、本人確認を行う認証ではありません。

## Authの参照用レコードを残す理由

既存DBでは `profiles.id`・`theater_logs.user_id`・同行者のIDが `auth.users` を参照しています。この互換性と既存記録を保つため、既存Auth行は削除しません。新規の名前にも管理用APIで参照用Auth行を作成します。ランダムな内部パスワードは利用者に入力・表示させず、アプリではパスワード認証を呼びません。

同じ正規化名から常に同じ内部メールを生成するため、Supabase Authのメール一意制約が同時登録も防ぎます。通常の既存名は登録前に `profiles` から確認し、名前の登録が途中で失敗した場合は新規作成分だけを取り消します。既存の名前・記録を削除して登録し直す処理はありません。

DBの変更・移行SQLは不要です。既存の `SUPABASE_SERVICE_ROLE_KEY` をサーバー側の新規登録と書き込みに使用します。ブラウザには渡しません。

`profiles.id` や既存Auth行を管理画面から削除すると外部キーの削除連動で記録を失う可能性があるため、名前の表記修正は `profiles.display_name` を編集します。Table Editorで直接編集するときは、別の登録名と重複させないでください。
